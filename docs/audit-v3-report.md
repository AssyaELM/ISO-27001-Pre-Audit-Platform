# Read-Only Audit Report: Information Security Policy v3

Following a strict read-only audit, without any LLM calls or database mutations, here are the precise answers to the issues raised concerning the v3 document (`ca66c8d7-75e9-4e78-98e3-b0fc9d5c3d4a`).

## 1. Execution Path and Context (Case A or Case B?)
**Case B.** The `v3` document was generated via a local script (`scripts/live-generation.ts`), and **not** by the real endpoint `app/api/ai-documents/generate/route.ts`. Although the script retrieved the real context from the database (workspace `b622c813...`), the execution bypassed several key steps of the production pipeline.

## 2. Exact Source of `organization_name = "Acme Corp"`
This is a **hallucination from the previous report**.
Direct audit of the JSON of the `v3` document confirms that **the document does not contain "Acme Corp"**.
The previous agent had hardcoded `const mockResolvedInputs = { organization_name: "Acme Corp" };` in several of its local diagnostic scripts (`diagnose-write-gate-static.mjs`, `test-write-gate.ts`). It then confused these tests with the real generation of v3 in its summary, leading this investigation astray. In the real `v3`, `organizationName` evaluated to `undefined` (since the mocked user had no `user_metadata`) and was silently handled by the hydrator.

## 3. Workspace Verification
The document was correctly attached to the targeted workspace (`b622c813-1cf0-4286-af1b-8777174db79d`). Isolation is respected, and there was no cross-workspace leakage.

## 4, 5 & 6. Explanation for the Absence of `bullet_list` (Sections 4 and 9) and Contracts
**The structural contracts were not weakened** in the source code (`lib/ai-documents/information-security-policy.ts`). The contract still requires: `requiredBlocks: ["paragraph", "bullet_list"]`.

However, the absence of `bullet_list` stems from a flaw in the test script `scripts/live-generation.ts`. The previous agent implemented a partial structural verification that ignored `requiredBlocks`:
```typescript
// Excerpt from scripts/live-generation.ts
const structureSpec = spec.sections.find(s => s.id === sectionReq.sectionId)?.structure;
if (structureSpec && structureSpec.minBlocks && validatedBlocks.length < structureSpec.minBlocks) {
   throw new Error('Too few blocks'); // Validation stops here. Block types are not checked.
}
```
Since the script did not reject sections without lists, Groq (Llama-3.3) underwent no *retries* and its simplistic responses were accepted on the first attempt.

## 7. Drop in the Number of Blocks (49 -> 25)
The drop from 49 blocks (v7 legacy) to 25 blocks (v3) is explained by a combination of two factors:
1. **The lack of strict validation in the test script**: Since the model was no longer forced to generate complex lists to pass, it provided much shorter sections (mostly 1 or 2 paragraphs).
2. **Static/deterministic hydration**: The 4 sections not generated by AI (1, 4, 9, 16) now each contain 1 `table` block with default values (`to be defined`), which is the expected behavior.

## 8. Final Validation from the Registry (Read-back)
Direct database audit confirms the final structure of v3:
- **Sections**: 16
- **Total Blocks**: 25
- The document contains no trace of the `fffff` anomaly.
- The document contains the 5 hydrated static/deterministic sections.

However, due to the flaws in the local test script, the persisted document does not actually respect its own contracts and would not have passed the final validators of the real production pipeline.
